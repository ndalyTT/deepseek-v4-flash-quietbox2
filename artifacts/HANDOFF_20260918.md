## 3. Operating rules (learned the hard way)

- **Reset once, then launch the server as the first fabric init. Never run a
  smoke or mesh open before the vLLM launch.** This replaces section 2 of the
  Aug 27 checklist. Exact sequence:
  ```bash
  cd /home/ttuser/deepseekv4flash
  pgrep -af 'vllm|EngineCore|harbor|run_deepseek'      # must be empty
  docker ps --format '{{.Names}}' | grep '^tt-model-'  # must be empty
  timeout 180 tt-smi -r
  export SMOKE_RUNS=0
  nohup terminal_bench_2_1/run_cust901_intermittency_check.sh > terminal_bench_2_1/logs/launch_$(date -u +%Y%m%dT%H%M%SZ).log 2>&1 &
  # waits for /health on 127.0.0.1:8010 (about 25 min), leaves the server up
  ```
- Never run `tt-smi` while the server owns the devices. Serialize every TT
  command. No reset loops, no flashing.
- Relay next (`run_deepseek_harness_unix_relay.sh` under `script`, expect
  `READY ... upstream_model=deepseek-ai/...`), then any request. Sequential
  requests only; the server is batch one.
- Closeout: SIGTERM the relay python by PID, SIGTERM the vLLM APIServer by
  PID, confirm `pgrep` empty, then `tt-smi -ls --local`.
- Tooling: the auto-mode permission classifier intermittently denies
  `tt-smi -r` and the launch script; the identical plain command alone passes
  on retry. Never `pkill -f <name>` from the tool shell; it kills the shell.
  Harbor trial dirs come back root-owned; `sudo -n chown -R ttuser:ttuser`
  before syncing the publish repo.
- Publishing: sync with `publish/deepseek-v4-flash-quietbox2/tools/sync_from_workspace.sh`,
  commit, push (authorized for the two repos only). tt-metal commits use
  `--no-verify`.

to fix. Every probe below runs against ONE server launch (rule above) with a

### 4b. Quantization (days, re-qualify with the Aug gates)

Budget: 33.39 GB allocated of 33.91 GB usable per device, ~0.5 GB free at
131k context. Routed gate/up in BFP2 = 14.4 GB/device; in BFP4 = 28.9 GB.
Promoting one layer BFP2 -> BFP4 costs ~0.34 GB. Today: 8 salient layers BFP4,
35 layers BFP2 (`selective_bfp4_salience8`).

1. Trade context for precision: 32k or 64k context frees roughly 0.5-0.8 GB
   (KV cache + RoPE tables) = one or two more BFP4 layers. Free.
2. Per-expert salience instead of per-layer: keep frequently routed experts
   in BFP4 across all layers, cold experts in BFP2. Load-time policy change
   in the tt-metal model code, no kernel work. Best quality per byte.
3. Better rounding into the same BFP2 grid at load time: per-output-channel
   pre-scaling folded into the next op (SmoothQuant style) and Hessian-aware
   rounding with a small calibration set (GPTQ style). Same memory, zero
   kernel changes. Highest leverage if P3 blames the weights.
4. Not worth it: expert offload over PCIe (Gen4 x4, far too slow per token).

### 4c. Kernel / throughput track (weeks, independent of quality)

Kernels are ours to edit: `tt-metal/` fork carries the TTNN ops and RISC-V
kernels. Decode is 150 ms/token (3.2 ms/layer), overhead-bound not
bandwidth-bound; prefill is ~41 tok/s (130k prefill = 53 min).

1. Two-ERISC fabric: drop `TT_METAL_DISABLE_FABRIC_TWO_ERISC=1` (the
   workaround dates from fw 19.11; the Nemotron container ran two-ERISC +
   STRICT_INIT on 19.13.1 for 30 h). Bounded test under the reset-then-launch
   rule. Direct collective-latency win if stable.
2. Fusion in the decode layer: norm+matmul, MoE gather/scatter, fewer
   collectives per layer. The Aug 23 candidate pass
   (`doc/optimized_multichip_decoder/candidate_summary.csv`) already rejected
   the tuning-only candidates as neutral; remaining wins are fusion.
3. Prefill: enable chunked prefill in the adapter and a flash-style attention
   kernel for long context. Dominates wall time for agentic transcripts.
4. Batch > 1 only after the above; the server is batch one today.
